**1c.** Open `trajectories.npz` in Python and verify:
- Shape of `epsilon`, `sigma`, `eps_p` is (200, 61, 3): 60 time steps plus t = 0.
- A few trajectories visualized as stress-strain curves (use `matplotlib.pyplot.plot(epsilon[i, :, 0], sigma[i, :, 0])`). Confirm you see hysteresis loops in the trajectories that yield, and straight lines in the ones that do not.
- How many trajectories keep yielding after the first cycle: `(np.abs(np.diff(eps_p[:, 20:], axis=1)).max(axis=(1, 2)) > 1e-10).sum()`.

What to expect (measured on the course data, `measured_results.md` §1):
- **The path.** Every path goes 0 → +a → −a → 0 three times. The strain direction stays fixed and only its sign flips, so no path is non-proportional. Trajectories 0–99 scale one random strain direction; 100–199 draw each component separately.
- **Who yields.** 134 of the 200 yield, and every one of them yields again in every cycle, in both directions: on the way out to +a and, after an elastic stretch of unloading, in reverse on the way out to −a. (Here a is the amplitude *vector*, so "+a" need not mean positive ε_xx.) Each yielding trajectory therefore draws hysteresis loops: the *strain* path closes every cycle, but the stress–strain curve does **not** close exactly, because the plastic state changes each cycle — the branches drift, cycle after cycle. For 127 of the 134, the σ_xx–ε_xx curve passes through both the first and the third quadrant. The one-liner above prints 134. The other 66 never yield and stay on one straight line.
- **The history (yielding trajectories only).** After a plastic excursion, the stress at ε = 0 is generally not zero (|σ| > 0.01 in 132 of the 134 at the end of the first cycle): the loading holds the strain at zero, so a residual stress remains in the element (a freed specimen would not show this). At matching peak strains, the stress *magnitude* |σ| grows each cycle (isotropic hardening). So for these trajectories the same strain maps to different stresses depending on where the path has been. The 66 never-yielding trajectories have no history: the same strain always gives the same stress.

### Task 2 — Stateless MLP baseline (20 points)

**2a.** Run `python stateless_mlp_baseline.py --data trajectories.npz`. This trains an MLP that takes ε(t) and predicts σ(t), ignoring history. On ARCC, run it as a job: `sbatch train_constitutive.sbatch stateless`, from the folder that holds the script and `trajectories.npz` (under a minute in our runs).

**2b.** Inspect `stateless_baseline.png`; it shows the three held-out trajectories with the most plastic flow, all of them loops. You will see: the MLP draws one curve through the middle of each loop and follows neither branch — at one strain it can return only one stress. Quantify the test MSE (the script prints it). Where is the error: on the held-out trajectories that never yield, or in the loops?

**2c.** Run again with `--include-plastic-strain` (`sbatch train_constitutive.sbatch stateless_with_q`); this run writes `stateless_with_q.png`. Now the MLP takes (ε(t), ε^p(t)) — adding the internal variable. Inspect `stateless_with_q.png`. The MLP now tracks the loops correctly because ε^p captures plasticity history.

**2d.** Report both MSEs in `prompts_task2.md`. The conclusion: stateless MLP *can* model plasticity if you feed it the internal variables explicitly; *cannot* if you don't. Note what 2c does *not* do: it is handed the true ε^p at every step, so it maps the current (ε, ε^p) to stress, but it never learns how ε^p evolves. A model that has to run on its own in a solver also needs that update.

## Hints

- **The MOOSE J2 setup may need tweaks** depending on your MOOSE version (it runs unchanged with the course build on ARCC). If `IsotropicPlasticityStressUpdate` is not the right class name, look at the MOOSE documentation for the current name (e.g., `IsotropicPlasticityStressUpdate` vs `PlasticityStressUpdate` vs other variants).
- **The Voigt factor of 2** strikes again: when reading `plastic_strain_xy_avg` from MOOSE, multiply by 2 to get the engineering shear plastic strain. The data generator handles this.
- **For Task 3**, the LSTM batch dimension is *trajectories*, not *time steps*. PyTorch's `nn.LSTM` with `batch_first=True` expects input shape `(B, T, 3)`.
- **If your stateless MLP somehow gets the cyclic loops right** without `--include-plastic-strain`, you've probably bugged the train/test split (likely leaking time steps from train to test). Verify split is by *trajectory*, not by step.
